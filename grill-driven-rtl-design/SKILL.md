# Grill-Driven RTL Design

把“文档草稿 + 用户逐点确认”转换成可审查、可综合、可验证的 RTL。核心原则是先确认协议语义和时序，再写一小段代码；每次确认都沉淀为文档或代码注释，避免一次性猜完整个模块。

## 工作顺序

1. 先读取设计文档、现有 RTL、接口定义和项目规则。不要先写代码；先列出已明确约束、矛盾点和第一个待确认问题。
2. 使用 grill-with-docs 的单问题节奏：一次只问一个会改变 RTL 结构或时序的问题，并给出推荐选项及原因。用户确认后才进入下一问题。
3. 将回答改写成可检查的规则：状态进入/退出条件、采样窗口、计数范围、输出保持条件、错误优先级和握手关系。优先补充设计文档中的流程小节或时序表。
4. 按协议时间顺序增量实现：先接口和输入采样，再同步/帧头检测，再对齐计数，再数据采样，再校验和错误，再结果输出与握手。不要为了“先能编译”把未讨论的功能随意置零。
5. 每一小步修改前遵守仓库规则：检查 `git status`，提交当前需要保留的工作区变更，提交成功后再编辑。修改后做最小语法检查，并说明下一步待确认点。

## 质询重点

按下列顺序逐个确认，已由文档明确的内容不要重复询问：

- 模块边界：单通道还是多通道；仲裁是否属于上层；`channel/busy` 与 `valid` 是否分别表达占用和结果有效。
- 采样模型：输入时钟、过采样倍数、滑动窗口方向、半码元/码元边界，以及多数表决使用哪些采样点。
- 同步与对齐：同步头编码、电平含义、检测发生在哪个状态；进入同步状态后补齐多少拍，哪一拍开始判决第一位数据。
- 数据路径：位序、左移/右移方向、数据位计数终值、曼切斯特合法性判定和非法时的状态去向。
- 字尾与校验：奇偶校验定义、校验位采样位置、字尾稳定窗口，以及连续字头是否属于正常协议场景。
- 输出协议：结果在哪一拍产生；`valid`、数据和错误是否保持；`ready` 握手、未握手新结果覆盖、复位和 `enable` 改变时的行为。

问题必须指向可观测行为。例如不要问“这个状态机可以吗”，要问“检测到同步头的当前拍进入 SYNC，随后补齐 14 拍，再进入 DATA；这样第一位数据的 16 点是否落在窗口 `[31:16]`？”

## RTL 组织要求

结合 `synthesizable-human-rtl` 和 `rtl-human-style` 执行：

- 新 RTL 默认使用 SystemVerilog；状态机采用三段式：状态寄存器、状态转移判定、状态相关输出/动作。
- 状态机转移判定使用 `// 状态机转移判定`，状态寄存器使用 `// 状态机更新`；不要用冗长的“第一段/第二段”标题。
- 每类寄存器使用独立 `always_ff`，状态相关处理采用 `case (state_reg)`，使同步头、对齐计数、数据计数、错误寄存器和输出保持逻辑各自清晰。
- 每个变量在同一行右侧写用途注释；同类变量连续排列，不在同类声明之间插空行。跨功能分组才空行。
- 注释解释协议时间和原因，使用“进入这一拍、补齐 14 拍、进入 DATA 一拍，正好……”这类可读描述；不要只写计数器名称。
- 不写冗余自保持赋值；组合逻辑给出完整默认值；避免不可综合语法、隐式锁存和多处驱动。
- 对滑动窗口在判决拍使用“移入当前输入后的 next window”，避免非阻塞赋值读到旧窗口。
- 语义不重叠的错误分别锁存，最后在结果输出处汇总；不要在多个层次重复判定同一错误。

## 每步交付格式

完成一个增量后，用短记录说明：

1. 本步确认的规则；
2. 修改了哪些变量/状态/时序块；
3. 如何检查（语法、断言或定向仿真）；
4. 当前仍未决定的一个问题；
5. 下一步只实现什么。

若用户纠正了写法，把纠正提炼成通用规则并更新本技能或项目技能，而不是只修当前一行。

## RTL 到 TB 的衔接

RTL 主流程确认后再写 TB。先用真实参考发送器覆盖正常协议行为，再通过输入波形层注入错误；不要为了适应当前 RTL 的缺陷而排除协议上正常的连续字。独立 TX/RX 时钟应先覆盖不同初始相位；频偏只有在规格给出容差后才加入。

TB 编译或仿真后清理 `xsim.dir`、`xvlog.log`、`xvlog.pb` 等生成物，只保留源文件、验证计划、审查记录和用户明确要求的波形。
