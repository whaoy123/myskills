# Engineering Design Fact Base

## 1. 目标

这个 Skill 只做一件事：

> 把讨论中已经形成的设计信息维护成稳定的工程事实库，使后续规格书、方案书、设计说明、PPT 和代码文档都从同一份事实来源取数。

基本流程：

```text
讨论 / 资料 / 测试
      ↓
提取新增或变化的信息
      ↓
判定状态与来源
      ↓
更新 PROJECT_FACTS.md
      ↓
其他文档从事实库读取
```

事实库不是正式文档，不追求行文漂亮，只追求：

```text
准确 > 可追踪 > 完整 > 好看
```

---

## 2. 职责边界

本 Skill 负责：

- 记录用户明确确认的设计决定；
- 记录已经确定的参数、器件、接口、结构和约束；
- 保存候选方案；
- 保存未决问题；
- 保存已否决方案及其原因；
- 保存被新方案替代的旧决定；
- 识别新信息与现有事实之间的冲突；
- 维护设计变更历史；
- 在有可靠来源时记录来源。

本 Skill 不负责：

- 把事实库润色成正式文章；
- 为了让文档完整而自动补设计；
- 根据常识替用户做尚未确认的工程决定；
- 把测试现象自动推断成故障原因；
- 把候选方案写成最终方案；
- 生成没有事实依据的背景、意义、优势和总结。

正式文档写作应由其他文档 Skill 或人工完成。

---

## 3. 默认文件

默认事实库文件名：

```text
PROJECT_FACTS.md
```

如果项目已经有事实库文件，则优先更新现有文件，不重复创建第二份。

如果用户明确指定文件名或路径，使用用户指定的位置。

---

## 4. 信息状态

事实库中的设计信息必须明确区分状态。

### `CONFIRMED`

已经被用户明确确认，或者已经被正式项目资料确定。

```md
- [CONFIRMED] 1553B 总线速率：1 Mbps。
```

### `CANDIDATE`

已经进入候选，但尚未最终确定。

```md
- [CANDIDATE] 继电器：TE Axicom IM03GR。
- [CANDIDATE] 继电器：Hongfa HFD4-K/4.5。
```

### `OPEN`

当前尚未解决，需要后续继续确认。

```md
- [OPEN] 1553B 耦合变压器最终型号。
```

### `REJECTED`

已经讨论过并被否决。

必须尽量保留否决原因，避免后续重新提出同一个方案。

```md
- [REJECTED] 使用普通低频信号继电器替代当前候选器件。
  - 原因：高频寄生参数和阻抗连续性尚不能保证。
```

### `SUPERSEDED`

过去曾经有效，但后来被新的设计决定替代。

```md
- [SUPERSEDED] 系统采用三板结构。
  - 替代方案：两板结构。
```

旧信息不要因为被替代而直接删除。

---

## 5. 状态判断规则

用户语言通常按以下方式理解：

```text
“就用这个 / 定这个 / 按这个做”       → CONFIRMED
“先放候选 / 方案里保留”              → CANDIDATE
“后面再定 / 还没确定 / 待确认”        → OPEN
“这个不要 / 排除 / 不考虑了”          → REJECTED
“改成这个 / 原方案换掉”               → 旧项 SUPERSEDED + 新项 CONFIRMED
```

如果用户只是讨论一种可能性，不要主动把它升级为 `CONFIRMED`。

如果状态无法可靠判断，保留为 `OPEN` 或 `CANDIDATE`，不要替用户做决定。

---

## 6. 每轮讨论的处理方式

不要每轮重新总结整个项目。

每次只检查本轮相对现有事实库发生了什么变化：

1. 新增了什么事实；
2. 哪些参数或决定被修改；
3. 哪些候选被确认或否决；
4. 出现了哪些新的未决问题；
5. 是否出现与旧事实冲突的信息；
6. 是否需要留下变更记录。

主干：

```text
现有事实库
   +
本轮新增信息
   ↓
差异识别
   ↓
状态判断
   ↓
冲突检查
   ↓
最小更新
```

只改真正发生变化的内容。

---

## 7. 事实记录格式

每条记录尽量满足：

```text
对象 + 决定/参数 + 状态
```

例如：

```md
- [CONFIRMED] 主控 SoC：Zynq-7020。
- [CONFIRMED] DDR 容量：1 GB。
- [CONFIRMED] Linux：PetaLinux。
- [OPEN] Linux 与 1553B 数据缓存的 DDR 分区比例。
```

优先记录可直接使用的信息，不要写抽象形容词。

推荐：

```md
- [CONFIRMED] 总线速率：1 Mbps。
- [CONFIRMED] 字长：20 bit。
- [CONFIRMED] 数据位：16 bit。
- [CONFIRMED] 最大数据字数量：32。
- [CONFIRMED] 时间戳分辨率：10 ns。
```

不要写：

```md
- 高速通信。
- 高精度时间戳。
- 支持较长消息。
```

## 9. 设计决定与原因分开

设计决定和决定原因属于不同信息。

例如：

```md
### 设计决定

- [CONFIRMED] 主控板按照最终完整接口一次设计。

### 原因

- 避免后续前级采集板扩展时再次修改主控板。
```

只有用户、项目文件或可靠证据明确给出原因时，才能把原因写入事实库。

AI 自己推测的理由不能写成既定事实。

---

## 10. 来源记录

如果事实来自外部证据，尽量记录来源。

来源可以是：

- 用户明确设计决定；
- 数据手册；
- 标准；
- 原理图；
- BOM；
- 项目需求文件；
- 测试记录；
- 官方网页；
- 论文或其他技术资料。

示例：

```md
- [CONFIRMED] ADS8688 输入范围：±10.24 V。
  - 来源：ADS8688 Datasheet。
```

如果只是用户做出的项目选择：

```md
- [CONFIRMED] 主控板预留 40 路 ADC 资源。
  - 来源：设计讨论。
```

不要伪造来源，也不要把“AI 推断”伪装成资料结论。

---

## 11. 测试事实与原因判断分开

测试现象本身可以记录，但不能未经分析直接转化为设计结论。

例如：

```md
### 测试记录

- 2026-08-25：PMG 首级差分输出 2.564 V。
- 2026-08-25：OPA197 输出 -12.5 V，并伴随明显噪声。
```

不能自动写成：

```md
- OPA197 电路设计错误。
```

只有原因完成验证后，才能另行加入：

```md
- [CONFIRMED] 故障原因：……
  - 验证方法：……
```

---

## 12. 冲突处理

新信息与已有事实冲突时，禁止静默覆盖。

处理顺序：

```text
发现冲突
  ↓
判断用户是否明确改变方案
  ├─ 是 → 旧项 SUPERSEDED，新项按新状态记录
  └─ 否 → 保留旧事实，并把冲突列为 OPEN
```

例如用户明确说：

> 原来用 Zynq-7045，现在改成 Zynq-7020。

应更新为：

```md
- [SUPERSEDED] 主控 SoC：Zynq-7045。
- [CONFIRMED] 主控 SoC：Zynq-7020。
```

如果只是资料中出现另一个型号，但用户没有表示切换，不要自动修改现有决定。

---

## 13. 变更历史

以下变化建议进入历史记录：

- 已确认参数发生改变；
- 系统架构发生改变；
- 器件型号发生替换；
- 接口定义发生改变；
- 已确认方案被否决；
- 重要设计边界发生改变。

记录格式：

```md
### 2026-09-16

- 修改：主控 SoC 型号。
- 原值：Zynq-7045。
- 新值：Zynq-7020。
- 原因：资源重新评估后调整。
```

如果用户没有说明原因，不要自行补原因，可写：

```md
- 原因：未记录。
```

## 14. 文档生成时的使用规则

其他 Skill 或 AI 根据事实库生成正式文档时，默认按以下规则使用信息：

```text
CONFIRMED   → 可以作为确定设计写入正文
CANDIDATE   → 只进入方案比较、候选设计或待选型部分
OPEN        → 只能作为待确认项，不得写成既定设计
REJECTED    → 默认不进入正式方案，只在决策历史需要时引用
SUPERSEDED  → 只用于历史追踪，不作为当前方案
```

正式文档不得因为“上下文看起来合理”而添加事实库中不存在的新设计决定。

如果需要增加设计内容，应先回到设计讨论，确认后写入事实库，再生成文档。

## 15. 与写作 Skill 的关系

推荐工作流：

```text
工程讨论
  ↓
engineering-design-fact-base
  ↓
PROJECT_FACTS.md
  ↓
具体文档生成 / 人工整合
  ↓
engineering-doc-style / humanizer
  ↓
最终文档
```

本 Skill 负责“记对”。

`engineering-doc-style`、`humanizer` 或人工负责“写得能看”。

两层不要混在一起。

---

## 16. 默认交互行为

如果用户只是继续进行工程讨论：

- 优先识别本轮形成的新事实；
- 不要每轮把完整事实库重新贴出来；
- 如果具备项目文件写入能力，可以按本轮变化更新事实库；
- 如果没有文件写入能力，只保留待更新差异，不要假装已经落盘。

当用户说：

> 更新一下事实库

优先输出或执行增量更新：

```md
### 本轮新增
- ...

### 本轮修改
- ...

### 状态变化
- ...

### 新增未决问题
- ...
```

当用户说：

> 给我完整事实库

再输出完整 `PROJECT_FACTS.md`。

---

## 17. 禁止行为

禁止：

1. 为了完整而补充不存在的参数；
2. 把候选方案写成最终方案；
3. 把 AI 推断写成用户确认事实；
4. 新方案出现后直接删除旧方案历史；
5. 将测试现象直接等价为故障原因；
6. 用“提高可靠性”“便于扩展”“满足需求”等空泛句填充事实库；
7. 大段复制原始聊天记录；
8. 同一个事实无意义地重复保存在多个章节；
9. 未经确认改变已有设计决定；
10. 为了适配正式文档语气而修改事实本身。

---

## 18. 最终原则

整个工程的信息流应保持为：

```text
人的判断 / 已验证证据
        ↓
  PROJECT_FACTS.md
        ↓
规格书 / 设计说明 / PPT / 原理图说明 / RTL 文档
```

**事实只维护一次，表达可以生成多次。**
