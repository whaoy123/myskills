# 分层模型任务编排

把复杂任务组织为“主控决策—执行落地—主控验收”的闭环。主控负责质量和最终结论，执行者负责实际修改与测试。

## 第一关：先选择模型

触发后先检查当前 Codex 任务工具公开的可用模型及推理强度。不要写死或凭记忆列出模型。

在规划、读取工程或创建任务前，只问一次紧凑问题：

```text
这次请指定：
1. 主控/审核模型与推理强度；
2. 执行模型与推理强度；
3. 最大并发执行任务数。
```

同时列出当前实际可用的选择。若用户只指定执行模型，则当前任务继续作为主控；若用户要求推荐，优先建议能力更强的模型担任主控、速度或成本更合适的模型担任执行者。

不得静默替换用户明确选择的模型。模型或推理强度不可用时，说明具体限制并重新询问。

## 明确角色边界

### 主控/审核模型

- 澄清目标、范围、约束和验收条件。
- 只读检查工程、文档、依赖和现有修改。
- 给出总体方案并拆分无重叠的执行任务。
- 为每个任务规定文件所有权、接口、禁止事项和验证命令。
- 跟踪执行进度，审查代码、差异、日志和测试覆盖。
- 发现问题时退回原执行任务修正；不替执行者偷偷完成业务实现。
- 独立复跑高风险或新增验证，最后签署验收结论。

主控可以维护计划、审核意见和最终报告等编排产物，但默认不编写业务 RTL、软件代码或用户交付正文。

### 执行模型

- 只修改任务明确授权的文件。
- 按主控方案实现、测试、记录实际结果并清理临时产物。
- 保留用户已有修改，不扩大范围，不自作主张改变架构。
- 报告实际命令、计数、警告、失败和遗留项。
- 不宣称自己已经完成最终验收。

## 编排流程

### 1. 建立验收基线

读取必要上下文，形成简短计划。把用户目标改写为可判定的验收条件，包括：

- 交付文件或外部结果；
- 功能和兼容性要求；
- 必跑测试、静态检查或人工核对；
- 不能修改的内容；
- 清理和可复现要求。

存在会改变架构或外部状态的关键歧义时先询问；普通实现细节由主控作出保守假设并明确记录。

### 2. 拆分并行任务

按模块、文件所有权或验证阶段拆分。每个执行任务必须具体、有限、可独立完成，并包含：

```text
目标：
允许修改：
禁止修改：
输入与接口约束：
实现要求：
验证要求：
交付回报格式：
```

避免两个执行任务同时修改同一文件。确需共享文件时串行安排，并明确后一个任务必须基于前一个结果工作。

### 3. 创建可见执行任务

当用户调用本技能要求多窗口执行时，将其视为创建可见 Codex 任务的授权。优先使用项目任务，并根据项目是否为 Git 仓库选择正确环境：

- 非 Git 或要求直接操作当前目录：使用项目 `local` 环境。
- Git 项目默认使用独立 worktree；只有用户明确要求共享当前工作区时使用 `local`。

每个任务显式传入用户选择的执行模型和推理强度。创建数量不得超过用户选择的并发数和当前工具并发上限。任务标题应体现模块或阶段。

若当前环境没有可见任务工具，说明限制；只有用户接受时才改用内部子代理，不能假装已经打开多个窗口。

### 4. 跟踪而不干扰

使用任务等待/读取工具和游标跟踪进度，避免反复读取相同输出。执行期间向用户提供简短、事实性的阶段更新，长任务至少每 60 秒更新一次。

执行者遇到问题时，主控先检查证据，再通过原任务发送精确修订要求。除非任务边界已经失效，不新开重复任务。

### 5. 对抗式审核

执行任务返回“完成”不等于验收。主控逐项完成：

1. 检查最终文件清单和修改范围。
2. 阅读关键实现，不只看执行者总结。
3. 检查是否存在层级作弊、硬编码结果、无界等待、伪造覆盖、遗漏错误路径或用户修改被覆盖。
4. 对照方案、接口和验收条件逐条核对。
5. 查看原始测试日志、失败计数、警告和退出码。
6. 独立复跑新增、高风险或最终集成测试。
7. 核对临时目录、后台进程和外部副作用已经按约定收口。

任何一项不满足都退回执行任务修正并重新验证。不得因预算、等待时间或执行者自报通过而降低标准。

### 6. 最终验收

只有所有必需任务通过审核、验收测试实际通过且无未说明阻塞时，才宣布完成。最终回答以结果为先，至少包含：

- 完成交付及关键文件链接；
- 每项验证的准确结果；
- 主控独立复跑结果；
- 与参考实现或预期行为的已知差异；
- 未完成项和明确 TODO；
- 已创建可见任务的入口（若界面要求输出任务指令）。

不要把警告、差异测试、预期失败或未运行项目笼统写成“全部通过”。

## 安全与失败处理

- 模型分工不扩大用户授权范围；外部写入、发布、删除和破坏性操作仍按原任务权限执行。
- 执行任务共享工作区时先检查脏文件，禁止覆盖其他任务或用户的修改。
- 一个执行者失败时保留证据，优先在原任务修复；连续失败再缩小任务或重新派发。
- 主控模型若与当前任务模型不同，可创建一个专用主控任务提供方案和审核结论，由当前任务负责透明转交；不得隐瞒当前任务不能自行切换模型的事实。
- 用户中途改变模型、范围或优先级时，停止受影响任务并重新确认分工。

## 触发示例

- “用高级模型做方案和验收，Luna 极高负责写代码，可以开三个任务。”
- “主任务不要实现，拆给便宜模型并行做，最后你统一审核。”
- “用多个窗口把模块分别做完，主模型只负责 review 和最终回归。”
