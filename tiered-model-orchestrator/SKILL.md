# 多代理任务编排 V2

把复杂任务组织为：

```text
当前对话 = 主控 / Orchestrator
        │
        ├─ Explorer × N   只读调查、定位、方案对比
        ├─ Worker × N     实际实现和修改
        ├─ Tester × N     独立测试、复现、回归
        └─ Reviewer × N   对抗审核、找遗漏和风险
        │
        └──────────────→ 主控最终验收
```

核心原则：**当前对话本身就是主控。不要为了编排子代理，再额外创建一个高级模型聊天作为二级主控。**

## 1. 默认模型与并发

除非用户明确覆盖，默认使用：

```text
主控模型：当前对话所使用的模型
子代理模型：Luna
子代理推理强度：max
最大并发：在当前工具、环境和任务依赖允许范围内自动决定
```

不再要求每次触发都先询问模型和并发数。

只有以下情况才询问或说明模型选择：

- 用户明确要求指定主控模型、子代理模型或推理强度；
- Luna 或 max 在当前环境不可用；
- 当前工具公开的模型能力与用户要求冲突；
- 成本、延迟或权限约束会实质影响任务执行。

如果默认的 Luna + max 不可用，优先选择当前可用的最接近执行配置，并明确说明实际使用了什么；不得静默替换用户明确指定的模型。

## 2. 禁止无意义的二级主控

### 默认规则

当前对话直接完成以下职责：

1. 读取必要上下文；
2. 明确目标和验收条件；
3. 构建任务拓扑；
4. 创建和管理子代理；
5. 汇总结果；
6. 退回返修；
7. 独立审核；
8. 最终验收。

**不得采用以下默认结构：**

```text
当前对话
   ↓
新建一个“高级主控聊天”
   ↓
高级主控聊天再创建多个子代理
```

这会无意义地增加一层转发、上下文复制、沟通成本和状态同步风险。

### 仅在以下情况允许额外主控任务

- 用户明确要求另开一个独立主控任务；
- 当前对话没有任何子代理/任务编排能力，但另一个任务环境具备必要能力；
- 需要人为隔离权限、仓库、账号或完全独立的工作区，且该隔离本身就是需求。

即使出现这些情况，也必须说明为什么需要新增这一层。

## 3. 子代理模式与独立任务模式

### 默认：原生子代理

优先直接从当前对话派发原生子代理。适合：

- 只读调查；
- 工程理解；
- Bug 定位；
- 方案比较；
- 测试设计；
- 独立审核；
- 文件所有权清晰的小范围实现。

### 独立 Codex 任务 / worktree

仅在真正需要独立工作区时使用，例如：

- 多个 Worker 会同时大量修改不同模块；
- 任务持续时间长且需要独立 Git 状态；
- 用户明确要求可见的独立任务/窗口；
- 修改风险较高，需要用 worktree 强隔离。

不要为了“看起来像多代理”而额外开独立窗口。

非 Git 或必须直接操作当前目录的任务使用共享/local 环境时，先检查现有修改，禁止覆盖用户或其他代理的工作。

## 4. 角色池

主控根据任务需要动态选择角色，不要求每次所有角色都出现。

### Explorer

职责：只读调查和信息收集。

适合：

- 阅读不同模块；
- 查找潜在问题；
- 调研多种实现；
- 分析日志；
- 建立依赖关系；
- 独立提出风险点。

默认不修改业务文件。

### Worker

职责：按明确边界执行实际修改。

要求：

- 只修改授权文件；
- 遵守主控给出的接口和方案；
- 保留用户已有修改；
- 不扩大任务范围；
- 完成自己的验证；
- 报告实际命令、结果、警告和遗留项；
- 不宣称完成最终验收。

### Tester

职责：独立验证，不默认相信 Worker 的自测结论。

适合：

- 复现问题；
- 编写或执行测试；
- 回归；
- 边界条件；
- 负向测试；
- 静态检查；
- 检查退出码、日志、失败计数和告警。

Tester 原则上不直接替 Worker 修业务代码；发现问题后交回主控。

### Reviewer

职责：对抗式审查。

重点检查：

- 是否真正满足需求；
- 是否存在硬编码结果或绕过逻辑；
- 是否遗漏错误路径、边界条件和异常处理；
- 是否覆盖用户已有修改；
- 是否改变未授权接口；
- 是否留下临时文件、后台进程或外部副作用；
- 测试是否具有实际验证价值，而不是“测试通过但没测到东西”。

高风险任务可同时派两个独立 Reviewer，要求互不参考对方结论后再由主控合并。

## 5. 先构建任务拓扑，再决定并行

不要因为“能拆”就并行。

主控先把工作划分为节点，并标记：

- 读/写属性；
- 输入；
- 输出；
- 文件所有权；
- 前置依赖；
- 是否可并行；
- 验收条件。

例如：

```text
A：调查协议和接口，只读
B：修改模块 X
C：修改模块 Y
D：集成 X 和 Y，依赖 B/C
E：最终测试，依赖 D
```

调度为：

```text
A ───────────────┐
B ──┐             │
    ├─→ D ────────┼─→ E
C ──┘             │
```

### 并行准则

可以并行：

- 独立只读调查；
- 不同文件/模块且接口已稳定；
- 独立测试；
- 独立审核。

必须串行：

- 后一任务依赖前一任务输出；
- 两个任务需要修改同一文件；
- 接口尚未确定；
- 一个任务会改变另一个任务的输入或测试基线。

共享文件确需多人处理时，建立明确顺序，后一个任务必须读取前一个任务的最终结果后再继续。

## 6. 子代理上下文最小化

主控保留全局上下文，子代理只接收完成当前任务所需的信息。

禁止把完整长对话、全部项目背景或无关文件机械复制给每个子代理。

推荐任务包：

```text
TASK
要完成什么。

INPUT
完成本任务真正需要的文件、证据、上下文和前置结果。

OWNERSHIP
允许读取什么；允许修改什么。

CONSTRAINTS
禁止修改、接口要求、兼容性、用户特殊要求。

DONE WHEN
可判定的完成条件和必须执行的验证。

RETURN
修改清单、关键结论、实际测试结果、失败/警告、仍存在的风险。
```

任务包必须具体、有限、可验证。不要向子代理发送“把这个项目做好”之类无法验收的宽泛要求。

## 7. 建立验收基线

派发前，主控先把用户目标改写成可判定条件，至少覆盖：

- 最终交付物；
- 功能要求；
- 接口与兼容性要求；
- 不能修改的内容；
- 必跑测试或人工核对项；
- 清理要求；
- 已知风险和允许的残余差异。

只有会改变架构、外部状态或用户目标的关键歧义才询问。普通实现细节由主控作保守判断并记录。

## 8. 执行、汇总与返修

### 执行阶段

- 按任务拓扑创建不超过当前允许并发数的子代理；
- 优先让只读任务尽早并行；
- 写任务必须先明确文件所有权；
- 不为同一个问题重复创建多个无边界 Worker；
- 子代理完成后，主控读取实际结果和必要证据，而不是只看“完成”二字。

### 发现问题后的处理

原则上退回原 Worker 修复，保持上下文连续。

失败升级规则：

```text
第一次失败
→ 原 Worker 根据明确证据修复

第二次同类失败
→ 派 Explorer / Reviewer 独立分析根因

第三次仍失败
→ 主控重新审视方案、接口或任务拆分，再决定是否重新派发

仍无法解决
→ 停止无效循环，明确报告 blocker、证据和剩余选择
```

不得无限“修复 → 审核失败 → 再修复”。

## 9. 对抗式审核

Worker 返回完成不等于验收。

主控至少检查：

1. 实际修改文件是否符合授权范围；
2. 关键实现是否真正满足需求；
3. 是否存在层级作弊、硬编码、伪覆盖、无界等待或绕开验证；
4. 用户原有修改是否被保留；
5. 接口和依赖是否一致；
6. 测试是否实际运行；
7. 原始结果中的退出码、失败计数和警告；
8. 临时产物和外部副作用是否收口。

对于关键任务，再增加独立 Tester 或 Reviewer。

主控应独立复跑至少一组最关键、最高风险或最终集成验证；不能把“Worker 自报通过”当作最终证据。

## 10. 最终验收

只有以下条件同时满足时才能宣布完成：

- 必需任务均结束；
- 所有发现的问题已经修复或被明确接受；
- 必跑测试真实执行并达到验收标准；
- 主控已完成最终检查；
- 没有未说明的 blocker、失败、警告或副作用。

最终回答结果优先，至少包含：

- 完成了什么；
- 关键文件或产物；
- 实际验证结果；
- 主控独立复核结果；
- 仍存在的已知差异、警告或 TODO。

不要把预期失败、未运行测试、警告或部分通过笼统描述为“全部通过”。

## 11. 安全与边界

- 多代理编排不扩大用户授权范围；
- 删除、发布、外部写入和破坏性操作仍遵守原任务权限；
- 不允许 Worker 越权修改其他任务文件；
- 不允许 Reviewer 以“顺手修复”为理由绕过文件所有权；
- 共享工作区时必须保护用户和其他任务的现有修改；
- 用户中途改变范围、优先级或模型要求时，只重排受影响部分，不无意义重启全部工作。

## 12. 触发示例

- “这项工作拆几个子代理并行做，你最后统一审核。”
- “Luna max 负责执行，你就在当前对话做主控和验收。”
- “两个代理分别审核这个 RTL，发现问题后再派一个 Worker 修改。”
- “先并行调研三个方案，再由你决定选哪个实现。”
- “不要另开高级代理窗口，你直接调下面的代理干活。”
- “把不同模块分别实现，最后做独立测试和对抗审核。”
