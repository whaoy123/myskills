# RTL Design Doc

## 目标

`rtl_design.md` 用来记录：

> 这个模块准备怎么工作，以及哪些设计决定以后必须还能看懂。

它不是 RTL 的文字备份，也不要求在写代码前冻结所有实现细节。

设计文档应尽量稳定：如果内部状态机、寄存器、局部组合逻辑发生重构，但模块整体设计没有变化，文档不应频繁修改。

---

# 输入

进入本阶段前，至少应有：

- 已确认的 `module_contract.md`；
- 项目已有需求、协议资料和上下游接口；
- 已有 RTL 或已有设计文档（如果是增量设计）；
- 项目约束和已有设计习惯。

`module_contract.md` 决定模块对外做什么；`rtl_design.md` 决定模块内部采用什么主要设计思路完成它。

---

# 与其他 Skill 的配合

## `grill-me`

如果发现关键设计问题尚未确定，使用 `grill-me` 一次只确认一个问题。

必须问用户的情况包括：

- 会改变模块职责划分；
- 会改变外部可观察时序；
- 会改变错误处理语义；
- 会改变数据含义或记录格式；
- 会改变握手、超时、优先级、覆盖/丢弃策略；
- 会改变上下游模块如何理解本模块。

普通局部实现细节不需要追问，例如：

- FSM 拆 5 个还是 6 个状态；
- 中间寄存器名称；
- 一个复杂条件拆成几个组合信号；
- `always_ff / always_comb` 的局部组织方式。

## `engineering-doc-style`

如果可用，最终文档必须应用该 Skill 的工程写作风格：简洁、直接，不写防御性长文，不把一个设计决定扩成多段重复解释。

# 核心原则

## 1. 记录设计意图，不复制 RTL

如果一段内容只是把 RTL 改写成文字或伪代码，优先删除。

例如不要写：

```text
if (state == CHECK && parity_ok && data_done)
    valid_o = 1
```

应该写：

> 当前字完整形成后，对外产生一次有效结果；结果未完成交付前保持不变。

## 2. 设计文档不要求实时领先代码

开发中允许先修改 RTL、仿真、确认方案是否成立，再在稳定后同步文档。

不要形成：

```text
发现问题 → 改文档 → 改 RTL → 再发现问题 → 再改文档
```

对于试验性实现和纯实现 Bug，不要求立即更新设计文档。

## 3. 只有设计决策变化才回写

需要回写：

- A 原来负责一件事，后来正式新增另一项职责；
- 数据流或消息流程发生变化；
- 记录格式、错误语义、握手语义发生变化；
- 超时起点、完成条件、优先级等关键时序语义改变。

通常不回写：

- FSM 状态数变化；
- 中间寄存器变化；
- `valid` 内部实现从 `a` 改成 `g`，但外部含义不变；
- 修复 off-by-one、漏条件、多驱动等纯 RTL Bug；
- 代码重构但行为不变。

# rtl_design.md 应覆盖的内容

设计文档不强制所有模块使用完全相同的表格，但应覆盖以下几类信息中与当前模块真正相关的部分。

## 1. 职责划分

说明模块内部哪些事情由谁负责，以及与上下游模块如何分工。

例如：

- `gap_time` 在 RX 内部统计，上层只消费结果；
- BM 负责消息级错误判断，RX 只负责字级错误；
- AXI4-Lite Bridge 只负责协议转换，不负责寄存器语义解释。

这类内容如果改变，会影响系统结构，因此应写。

## 2. 主流程 / 数据流 / 事务流

根据模块本质选择最自然的表达方式。

可以是：

- 数据流；
- 协议阶段；
- 事务规则；
- 消息流程；
- 状态转换关系；
- 存储读写流程。

不要为了统一模板强迫所有模块使用同一种形式。

## 3. 关键状态和存储

只记录那些对理解设计真正重要的状态或存储：

- 为什么需要这个 FIFO / BRAM / 上下文寄存器；
- 它保存什么；
- 它在整个设计里承担什么作用。

不需要把所有寄存器逐个列成表。

## 4. 关键时序

必须写清会影响行为理解和后续 TB 判定的时序语义，例如：

- handshake 完成条件；
- 结果保持条件；
- 延迟；
- 计时起点和终点；
- 超时条件；
- 同拍事件优先级；
- 协议规定的时间窗口。

特别是计数器：

> 必须写“为什么开始计、什么时候清零、它代表什么时间”；不写计数器位宽、加法代码和所在 `always_ff`。

## 5. 关键设计语义

专门保留那些会影响：

- TB 的预期；
- 上层模块理解；
- 协议行为；
- 错误处理；
- 数据解释方式。

每条尽量 1～2 句话。

例如：

| 项目 | 已确定语义 |
|---|---|
| `valid_o` | 完整结果形成后拉高，未完成握手前保持 |
| 错误字 | 仍向上层交付，同时置错误标志 |
| 超时起点 | 以 RX 接收活动结束后的空闲时间为基准 |
| 同拍事件 | 如果完成事件和超时事件同拍，完成事件优先 |

判断标准：

> 如果这个选择改了，TB 的期望结果、上层理解或协议行为会跟着变，就应该写。

# 表达形式选择

## 类型 A：阶段 / 协议时序型

适合串行接收、编码解码、固定协议阶段。

例如 RX：

```text
差分输入 → 字检测 → 数据接收 → 校验 → 结果交付
```

可以配阶段时序表。

## 类型 B：事务规则型

适合 AXI、APB、寄存器桥、请求响应接口。

优先写“什么事件发生后必须满足什么规则”，而不是状态机伪代码。

## 类型 C：复杂控制型

适合 BM、RT、Cache、调度器等。

可以拆成：

- 主流程 / 消息流程；
- 存储格式；
- 特殊规则；
- 计时和错误语义。

必要时再补一张很小的状态职责表，但不要把整个 FSM 翻译成伪代码。

# 示例 1：1553B RX

RX 属于阶段 / 协议时序型模块。

## 职责划分

- RX 只负责单个 1553B 字的接收和字级判断；
- 消息级合法性由上层 BM/BC/RT 处理；
- 字间隔在 RX 内统计并随字结果一起输出。

## 主流程

```text
差分输入
  ↓
字开始检测 / 字类型识别
  ↓
16bit 数据接收
  ↓
字级校验
  ↓
数据 + 类型 + 错误 + gap_time
  ↓
valid/ready 交付
```

## 协议阶段时序

| 阶段 | 设计语义 |
|---|---|
| SYNC | 识别当前字的同步头和字类型 |
| DATA | 接收 16bit 数据 |
| PARITY / CHECK | 完成字级合法性判断 |
| RESULT | 形成一份完整字结果并等待交付 |

如果协议时长已经冻结，可以单独记录 3us SYNC、1us/bit 等协议时间；内部 FSM 状态名和采样计数器不需要复制进文档。

## 关键设计语义

| 项目 | 已确定语义 |
|---|---|
| 字级错误 | 错误字仍形成结果，由 `word_error_o` 标识 |
| 结果保持 | `valid_o=1 && ready_i=0` 时，当前结果保持 |
| 字间隔 | 统计前一字结束到当前字开始之间的时间 |

# 示例 2：AXI4-Lite Slave Bridge

AXI4-Lite Bridge 属于事务规则型模块。

## 职责划分

- 对外作为 AXI4-Lite Slave；
- 对内转换为简单寄存器读写请求；
- 不解释寄存器自身功能语义。

## 写事务规则

| 事件 | 规则 |
|---|---|
| 收到 AW | 保存当前写地址，不要求 W 同拍到达 |
| 收到 W | 保存数据和字节使能，不要求 AW 同拍到达 |
| AW 和 W 都完成 | 发起一次内部写访问 |
| 内部写完成 | 产生 B 响应 |
| `BVALID=1 && BREADY=0` | 写响应保持 |
| B 握手完成 | 当前写事务结束 |

## 读事务规则

| 事件 | 规则 |
|---|---|
| 收到 AR | 发起一次内部读访问 |
| 内部读结果形成 | 产生 R 响应 |
| `RVALID=1 && RREADY=0` | `RVALID/RDATA/RRESP` 保持 |
| R 握手完成 | 当前读事务结束 |

## 关键设计语义

- 首版只允许一个未完成访问；
- 读写同时到达时写优先；
- AW 和 W 是独立通道，不能假设同拍到达；
- 内部寄存器访问固定时序，不设置额外 ready/ack。

不需要记录 `IDLE / WRITE_CAPTURE / WRITE_ACCESS / WRITE_RESP` 等具体状态名。

# 示例 3：1553B BM

BM 属于复杂控制型模块。

## 职责划分

- RX 提供字级结果；
- BM 负责消息级识别、筛选、错误判断和记录形成；
- 存储模块负责后续记录管理和读取。

## 消息流程

| 消息类型 | 接收顺序 | 结束条件 |
|---|---|---|
| BC→RT | CMD → DATA×N → STATUS | STATUS 完成 |
| RT→BC | CMD → STATUS → DATA×N | 数据收完 |
| RT→RT | CMD1 → CMD2 → STATUS1 → DATA×N → STATUS2 | STATUS2 完成 |
| 广播 BC→RT | CMD → DATA×N | 数据收完 |
| 方式码 | 按方式码决定是否带 DATA / STATUS | 对应流程完成 |

这张表描述消息设计本身，不跟随 FSM 状态数变化。

## 记录格式

| Offset | 内容 |
|---:|---|
| 0 | 有效标志 + 通道 + 数据数量 + 消息类型 + 错误 |
| 1~2 | 64bit 时间戳 |
| 4 | CMD1 / CMD2 |
| 5 | STATUS1 / STATUS2 |
| 6~21 | DATA |
| 22 | 消息号 |
| 23 | 保留 |

关键规则：

- 两个 16bit 字按接收顺序合并为一个 32bit；
- 最后写 offset 0 的有效头；
- 有效头写入表示整条记录正式提交。

## 计时规则

| 计时项 | 起点 / 重置条件 | 计时条件 | 用途 |
|---|---|---|---|
| 字间隔 / 无响应 | RX 出现新的字接收活动 | RX 空闲期间累计 | 判断后续字是否超时 |
| RT→RT 首数据等待 | 第二命令对应协议事件完成 | 等待首数据期间累计 | 判断 RT→RT 首数据超时 |

这里必须保留“从什么事件开始计时”的语义，但不记录计数器具体实现。

## 特殊规则

| 情况 | BM 行为 |
|---|---|
| 首命令到达 | 开始一条新消息记录并获取时间戳 |
| 不符合监听条件 | 不形成有效记录 |
| 数据阶段收到错误字 | 标记当前消息错误并结束 |
| 等待后续字超时 | 记录对应超时错误 |
| 消息完成 | 写消息号并最终提交有效头 |

# 工作流程

## Step 1：读取 Contract 和项目上下文

先确认模块外部边界，不重复讨论已经冻结的 Interface / Purpose / Capabilities。

## Step 2：识别模块最自然的表达形式

优先判断它属于：

- 阶段 / 协议时序型；
- 事务规则型；
- 复杂控制型；
- 或其他更合适的形式。

不强制统一模板。

## Step 3：整理第一版设计

至少覆盖：

- 职责划分；
- 主流程；
- 关键存储 / 状态；
- 关键时序；
- 关键设计语义。

其中没有实际内容的部分可以省略，不为了模板完整而硬写。

## Step 4：确认关键缺口

凡是设计文档没有定死、但又会影响功能、职责、接口、关键时序、错误处理或数据语义的问题，都必须使用 `grill-me` 逐项问用户。

## Step 5：用户确认后进入 RTL Coding

此时冻结的是行为和关键设计决定，不冻结具体 RTL 结构。

---

# 通过条件

只有同时满足以下条件，`rtl_design.md` 才允许进入正式 RTL Coding：

1. **职责边界确定**
   - 模块内部主要职责及与上下游的分工没有关键歧义。

2. **主流程确定**
   - 数据、事务或消息从进入到结束的主要路径可以讲清楚。

3. **关键状态和存储确定**
   - 必须保存哪些上下文、为什么需要 FIFO/BRAM/寄存状态已经明确。

4. **关键时序确定**
   - handshake、保持、延迟、计时起点/终点、超时和关键优先级不存在核心歧义。

设计通过不要求：

- 所有 FSM 状态提前画完；
- 每个寄存器提前列出；
- 每个内部布尔条件提前确定；
- 把完整实现写成伪代码。

---

# RTL Coding 阶段的边界

进入 Coding 后，AI 可以自行决定普通局部实现，例如：

- FSM 具体拆几个状态；
- 中间寄存器和组合信号怎么拆；
- 局部代码组织方式；
- 在不改变设计语义的前提下做实现优化。

但只要发现一个设计文档没有定死、同时又比较关键的问题，必须停止猜测并询问用户。

RTL 和仿真稳定后，再统一同步 `rtl_design.md`。
