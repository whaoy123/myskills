# Engineering Document Style

## 1. 目标

把工程文档写成“以后自己回来还能快速看懂和继续工作的记录”，而不是论文、汇报材料或代码的文字备份。

默认目标：

- 先写结论、规则、接口、流程和关键决策；
- 只保留会影响理解、实现、验证或后续修改的信息；
- 允许表格、短列表、简图、短伪代码按内容选择，不强制统一表达形式；
- 不为了显得完整而扩写背景、意义、风险和免责声明；
- 不把源码逐行翻译成中文；
- 文档应比代码更稳定，避免随着局部实现变化反复打补丁。

## 2. 与其他 Skill 的关系

### humanizer

最终文字表达默认同时应用 `humanizer`：简洁、直接、去 AI 腔、去无意义防御性表述。

### grill-me

当文档对应的设计决策尚未确定时，可调用 `grill-me`：

- 一次只确认一个真正会影响结果的决策；
- 能从代码、现有文档、工具或环境查到的事实先查，不拿事实问题反问用户；
- 设计选择由用户确认；
- 未确认的关键决策不得静默补全。

### 领域专项 Skill

本 Skill 只负责“工程文档怎么表达”。具体内容由领域 Skill 决定，例如 RTL、PCB、测试、算法等。

## 3. 写作原则

### 3.1 文档记录稳定信息

优先记录：

- 模块/系统负责什么；
- 接口和数据含义；
- 主流程或事务关系；
- 关键存储和状态的用途；
- 关键时序、边界和错误语义；
- 会影响上下游、验证结果或后续维护的设计决策；
- 为什么选择某个结构，而不是某个局部布尔表达式怎么写。

通常不记录：

- 局部中间信号的组合表达式；
- 可以直接从代码一眼看出的赋值；
- 状态机每个分支的逐行翻译；
- 纯实现重构但没有改变外部语义的细节；
- 为了“完整”而添加的背景、免责声明、重复总结。

判断标准：

> 如果这个实现细节以后换一种写法，文档仍然应该成立，就写设计语义；如果文档必须跟着每次局部代码修改同步，通常写得太贴近实现了。

### 3.2 内容标准化，表达形式允许灵活

不要要求所有工程问题使用同一种模板。

根据内容选择最短、最清楚的形式：

- 接口：端口声明或表格；
- 顺序流程：箭头/阶段表；
- 事务协议：事件规则表；
- 复杂控制：流程表 + 关键规则；
- 存储布局：地址/字段表；
- 时序：事件 + 相对周期/时间范围；
- 少量复杂逻辑：必要时使用短伪代码。

伪代码只用于表达稳定流程，不用于复制 RTL 的完整 if/else 和寄存器赋值。

### 3.3 关键语义要短

影响下面任一项的设计决定必须记录：

- 上下游模块理解；
- TB 预期结果；
- 协议行为；
- 数据含义；
- 错误处理；
- 关键时序。

每条通常控制在 1～2 句话。复杂原因放在调试记录、代码注释或单独的决策记录，不把主设计文档写成长篇解释。

## 4. 更新文档的时机

开发过程中允许先修改实现、仿真和调试，不要求每次试验性代码修改前先改文档。

推荐顺序：

```text
发现问题/新增需求
→ 修改实现并验证
→ 设计稳定
→ 判断是否改变了设计语义
→ 只同步真正变化的文档内容
```

以下情况需要同步文档：

- 模块职责变化；
- 接口或数据语义变化；
- 主流程变化；
- 关键时序变化；
- 错误/边界处理变化；
- 存储格式、提交条件、计时基准等关键规则变化。

以下情况通常不需要同步主设计文档：

- 状态机拆分数量变化但行为不变；
- 中间寄存器/信号改名；
- 布尔表达式修正但外部语义不变；
- always 块重构；
- 纯综合/可读性优化。

## 5. 风格

默认：

- 中文；
- 先结论后解释；
- 用工程人员自然记录问题的方式写；
- 句子短，能用表格就不用多段解释；
- 不重复同一结论；
- 不加入“为了保证系统稳定可靠”“需要注意的是”“值得一提的是”等无信息量句子；
- 不写“本文不代表……”“本节不讨论……”一类防御性文字，除非边界本身就是必要设计信息。

如果用户已有同类文档样例：

1. 优先读取用户亲自写、且用户认可的段落；
2. 模仿其句长、用词、编号方式、表格习惯和信息密度；
3. 用户明确指出“不喜欢”的 AI 段落作为反例；
4. 样例风格优先于本 Skill 的通用格式建议。

## 6. 自检

写完或改完工程文档后快速检查：

- 有没有把代码重新翻译了一遍？
- 有没有写了实现改变就必须同步的脆弱细节？
- 有没有遗漏影响上下游/TB/协议理解的关键语义？
- 有没有同一件事解释两遍以上？
- 能不能删掉一段而不损失实际信息？
- 表格是否比当前长段文字更清楚？

如果答案显示内容过密，优先删减而不是继续扩写。
