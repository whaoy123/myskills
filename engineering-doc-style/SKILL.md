# Engineering Document Style

## 1. 目标

工程文档首先是给自己后续继续工作的，不是为了显得完整。

默认目标：

- 打开文档后可以很快知道现在怎么设计、为什么这么设计、还有什么没定；
- 先写结论、规则、流程和关键决策，再补真正需要的原因；
- 文档记录稳定设计语义，不做源码的中文备份；
- 根据内容选择自然表达形式，不强制所有内容套同一模板；
- 能少写就少写，但不能省掉会影响实现、验证或后续理解的关键信息。

---

## 2. 与其他 Skill 的关系

### `humanizer`

最终表达默认同时应用 `humanizer`，继续压缩 AI 腔、套话、重复总结和防御性文字。

### `grill-me`

设计本身还没确定时使用 `grill-me`：

- 能从现有代码、文档、工具中查到的事实先查；
- 真正的设计选择一次只问一个；
- 给推荐答案；
- 没定死的关键行为不能由 AI 静默补全。

### 领域专项 Skill

本 Skill 只负责“怎么写”。

具体应该记录什么，由 RTL、PCB、算法、测试等领域 Skill 决定。

# 3. 从用户工程笔记提炼出的写作习惯

这些规则优先级高于常规“技术文档模板”。

## 3.1 直接进入问题

不要先写泛背景。

推荐：

> MEM 存储不可能都在单周期完成，所以访存部分需要增加握手，中间等待过程进行反压。

不要改写成：

> 为了进一步提高系统在复杂访存场景下的稳定性与可靠性，本设计针对存储访问机制进行了进一步优化。

原则：

> 第一段就应该出现当前设计对象、问题或结论。

---

## 3.2 结论和原因放得很近

用户习惯不是单独开一个“设计依据”章节，而是在提出选择后直接说原因。

例如：

> FIFO 不需要管地址，但错误消息不方便覆盖，数据包顺序也不好控制。BRAM 可以随机访问，后续覆盖和消息管理都更方便，所以这里用 BRAM。

这种写法优先于：

```text
3.2.1 FIFO 方案
3.2.2 BRAM 方案
3.2.3 方案对比
3.2.4 最终选择
```

只有方案确实复杂时才拆开。

---

## 3.3 优先写因果链，不堆术语

用户笔记常用：

```text
现象/约束
→ 为什么会有问题
→ 所以要怎么改
→ 改完后会影响什么
```

例如：

> 原来的 stall 在顺序流水线里很好用，但是进入并行执行后语义开始不清楚。下级本身已经有 ready，再额外通过 stall 控制暂停会出现两套控制。所以 dispatch 之后统一改成 valid/ready 更清楚。

不要为了显得专业替换成大量抽象词：

- 系统性优化；
- 协同机制；
- 鲁棒性增强；
- 多维度提升；
- 架构层面赋能；
- 有效保障。

能说具体因果就不说抽象评价。

---

## 3.4 可以保留自然工程口吻

设计笔记允许自然使用：

- 所以；
- 也就是说；
- 比如；
- 但是；
- 这里；
- 这样的话；
- 本质上。

这些词可以帮助沿着设计思路往下读，不需要全部改成论文语气。

但不要机械模仿用户随手记录中的：

- 错别字；
- 缺失标点；
- 明显病句；
- 过长不分句；
- 临时口头词，如“库库往外发”一类只适合私人草稿的表达。

要模仿的是思考方式和信息密度，不是输入法痕迹。

---

## 3.5 不确定就直接留 TODO

还没想明白的地方，不要由 AI 补成一个看似完整的结论。

推荐：

```text
TODO：这里的超时应该从第二命令字结束开始计，还是从 RX busy 拉低开始计，需要再确认。
```

或者：

```text
TODO：确认异常和分支预测错误同拍发生时的重定向优先级。
```

不要写：

> 后续可结合具体场景进一步分析并进行适当优化。

TODO 应该指出**具体没定的东西是什么**。

---

## 3.6 举例优先用具体场景

抽象概念难解释时，用户倾向于直接造一个具体情况。

例如解释功能边界：

> 一共做 400 个 FFT，如果硬件一次只能并行 200 个，可以让上位机一次给 400 个，由固件拆成两批；也可以让上位机直接分成两批 200 个。由谁负责拆分，就是功能边界的一部分。

这种例子比再补一段抽象定义更有效。

---

## 3.7 标题只在真的换主题时使用

不要为了结构完整把三句话拆成四级标题。

适合建标题的情况：

- 设计对象变了；
- 从接口切到时序；
- 从正常流程切到错误处理；
- 从一个独立问题切到另一个独立问题。

不适合：

```text
## 设计背景
## 设计目的
## 设计原则
## 设计方法
```

如果这四段实际只在说一件事，就合并。

# 4. 草稿笔记和正式工程文档分开处理

## 4.1 草稿笔记模式

适用于：

- 设计过程中捋思路；
- 学习笔记；
- 临时问题记录；
- Debug 过程；
- 还存在 TODO 的方案。

允许：

- 更自然的口语连接；
- 问句；
- TODO；
- 先写当前直觉，后面再修正；
- 直接记录“这里原来怎么想，现在为什么改”。

不要强行把草稿整理成正式报告，否则容易把真正的思考过程抹掉。

## 4.2 正式工程文档模式

适用于：

- 设计说明；
- 接口说明；
- 方案定稿；
- 验证计划；
- 用户手册中的工程部分。

保留草稿中的核心结构，但：

- 去掉明显口头表达；
- 修正语病和标点；
- 合并重复推理；
- 已解决 TODO 删除或改成正式规则；
- 只留下最终仍然成立的设计意图。

正式化不等于扩写。

# 5. 内容选择规则

优先记录：

- 模块/系统负责什么；
- 为什么采用当前结构；
- 主数据流或控制流；
- 接口和数据含义；
- 关键存储为什么存在；
- 关键时序和时间基准；
- 错误处理和边界行为；
- 会影响上下游、验证或后续扩展的设计决定；
- 仍未解决的具体问题。

通常不记录：

- 局部中间信号的完整布尔表达式；
- 可以从代码一眼看出的赋值；
- FSM 每个分支的逐行中文翻译；
- 纯实现重构但行为没有变化的内容；
- 为了“完整”而添加的背景、意义、展望；
- 反复解释同一个结论。

判断标准：

> 如果局部代码换一种写法，文档仍然成立，这通常是值得记录的设计语义。

> 如果每改一个 if 都要同步文档，说明文档写得太贴实现。

---

# 6. 表达形式怎么选

内容标准化，形式不标准化。

| 内容 | 优先形式 |
|---|---|
| 简单因果、设计选择 | 1～3 个短段落 |
| 功能/需求清单 | 短列表 |
| 接口定义 | 端口声明或表格 |
| 多阶段顺序关系 | 流程箭头或阶段表 |
| 周期级时序 | 时序表 |
| 地址、字段、状态映射 | 表格 |
| 多种消息/事务类型 | 规则表 |
| 少量复杂控制关系 | 短伪代码 |
| 尚未解决的问题 | TODO 列表 |

表格不是为了好看。

只有当存在**横向比较、逐拍关系、字段映射、固定分类**时，表格才比自然语言更好。

# 7. 典型正例

## 7.1 一个简单规则就一句话

> 写协议时，错误条件和对应处理已经由协议定义，先按协议实现，不要自己重新发明错误语义。

不要扩成一整节“协议实现原则”。

## 7.2 握手时序直接说谁在什么时候做什么

> 发送方在数据有效后拉高 valid；接收方空闲时 ready 保持为 1；只有 valid 和 ready 同拍有效才算完成一次传输。

如果需要逐拍精确说明，再换时序表，不在同一段里重复三遍。

## 7.3 设计变化按问题推动

> 原来分支预测错误在 EX 冲刷。加入精确异常后，异常可能已经到 MEM/WB，而后续预测错误先在 EX 重定向，这样优先级不好处理。所以把预测错误的最终冲刷位置后移，再统一做优先级仲裁。

这里保留“为什么改”，不需要复制冲刷模块 RTL。

## 7.4 存储选择直接写取舍

> FIFO 顺序读写简单，但错误消息不好回滚，也不方便控制消息边界。BM 需要对消息记录做覆盖和提交，所以使用 BRAM。

# 8. 需要主动删除的 AI 写法

发现下面模式时优先重写：

### 空泛开头

- “随着……不断发展”；
- “为了进一步提高……”；
- “本节将系统介绍……”；
- “在现代复杂系统中……”；
- “该设计具有重要意义”。

### 无信息量评价

- 有效提升；
- 显著增强；
- 充分保证；
- 全面覆盖；
- 系统性解决；
- 为后续奠定坚实基础。

除非后面马上给出具体提升了什么、怎么验证。

### 防御性文字

- “需要说明的是……”；
- “值得注意的是……”；
- “这并不意味着……”；
- “本文不代表……”；
- “不排除未来……”。

真正必要的限制直接写限制本身。

### 机械总结

一节结尾不要自动再来：

> 综上所述……

如果前面已经说清楚，直接结束。

### 过度中英双语

不要自动写：

> 需求分析（Requirements）
> 框图设计（Block Diagram）
> 设计验证（Verification）

只有术语本身常用英文、需要和代码/协议对齐时才保留英文。

# 9. 文档更新方式

开发过程中允许：

```text
先发现问题
→ 改实现
→ 仿真/测试
→ 确认方案稳定
→ 再同步文档
```

需要回写文档的通常是：

- 职责变化；
- 接口变化；
- 主流程变化；
- 关键时序变化；
- 错误/边界语义变化；
- 存储布局、提交条件、时间基准等关键规则变化。

通常不因为下面情况修改主设计文档：

- 状态数变化；
- 内部信号改名；
- always 块重构；
- 局部条件表达式变化但设计语义没变；
- 纯综合和可读性优化。

---

# 10. 最终自检

写完后只检查这几件事：

1. 第一段有没有直接进入问题？
2. 每个设计选择附近有没有真正需要的原因？
3. 有没有把一句话能说完的东西拆成一节？
4. 有没有把代码重新翻译了一遍？
5. 有没有没想清楚却被 AI 自动补全的地方？有就改成明确 TODO。
6. 表格是不是确实比文字清楚？
7. 有没有“系统性、全面、有效提升、奠定基础”一类空话？
8. 同一个结论有没有说两遍？
9. 如果删掉某一段，实际信息是否完全不受影响？如果是，删掉。

总结：工程文档要保留的是设计思路和关键语义，不是文档的完整感。
