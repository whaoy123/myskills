# 多 Agent 协作 V3：策略层 + Ruflo 执行层

核心结构：

~~~text
当前对话 = 最终主控 / Policy Orchestrator
        │
        │ 目标、验收、边界、角色、返修、最终判断
        ▼
Ruflo = 执行层（可用时优先）
        │
        ├─ Swarm / Agent
        ├─ Workflow / parallel / pipeline
        ├─ Worktree isolation
        ├─ Status / Monitor
        └─ Execution memory
        │
        ├─ Explorer × N
        ├─ Worker × N
        ├─ Tester × N
        └─ Reviewer × N
        │
        └──────────────→ 当前对话最终验收
~~~

真正的分界点是：**本 Skill 决定“该怎么干、什么算完成”；Ruflo 负责“把多个 Agent 真正跑起来并管理状态”。**

## 1. 主控职责不外包

当前对话始终负责：

1. 读取必要上下文；
2. 明确目标和验收条件；
3. 构建任务拓扑；
4. 决定角色、模型、权限和文件所有权；
5. 选择 Ruflo / 原生子代理 / 独立任务作为执行后端；
6. 汇总证据并退回返修；
7. 组织独立测试和对抗审核；
8. 完成最终验收。

默认禁止：

~~~text
当前对话
   ↓
新建一个“高级主控 Agent”
   ↓
这个 Agent 再创建多个子 Agent
~~~

Ruflo 的 coordinator、hierarchical swarm 或 workflow 只是执行机制，不能替代当前对话的最终判断权。

只有用户明确要求独立主控，或权限/工作区必须完全隔离时，才允许新增一层主控。

## 2. 执行后端选择

按以下顺序选择能满足任务的最轻后端：

~~~text
Ruflo 可用
→ Ruflo

Ruflo 不可用，但原生子代理可用
→ 原生子代理

需要独立 Git 状态 / 可见任务 / 强隔离
→ 独立 Codex 任务或 worktree

以上都不可用
→ 当前对话串行执行
~~~

### Ruflo 可用时

优先把这些能力交给 Ruflo：

- Agent 创建、终止、状态查询；
- 多 Agent 并发与 swarm 协调；
- 可恢复 Workflow；
- parallel / pipeline 等确定性 fan-out；
- 多 Worker 的 worktree 隔离；
- 长任务状态与监控；
- 仅用于执行优化的短期/跨会话模式记忆。

不要在 Skill 里再次手工模拟同一套状态机。

### Ruflo 不可用时

继续使用本 Skill 原有规则执行，不把“没有 Ruflo”当成任务 blocker。

### 不自动安装或初始化

Ruflo 初始化可能向仓库写入 .claude/、.claude-flow/、CLAUDE.md、MCP 或其他配置。

**除非用户明确要求安装/初始化，否则不得因为触发本 Skill 就自动运行初始化。**

用户明确要求配置时，Windows 原生可优先使用：

~~~powershell
npx ruflo@latest init wizard
~~~

实际命令必须以当前 Ruflo 官方版本支持的接口为准。

## 3. Ruflo 能力映射

先按任务需要选择能力，不为了“多 Agent”而堆功能。

| 需求 | 优先机制 |
|---|---|
| 多个 Agent 并行调查/实现/审核 | swarm / agent |
| N 个独立对象做相同检查 | Workflow parallel |
| 每个对象依次经历多阶段处理 | Workflow pipeline |
| 需要暂停、恢复、人工确认 | 持久 workflow |
| 多 Worker 同时改代码 | worktree isolation |
| 查看运行状态、失败 Agent | status / monitor |
| 保存可复用执行模式 | Ruflo memory |

调用前先检查当前环境实际暴露的 Ruflo 工具和版本；不要假定某个 MCP 名称一定存在。

### Memory 边界

Ruflo memory = **执行层记忆**，用于成功模式、任务结果、调度经验和可复用解决方案。

它不替代项目事实源：

- 稳定工程事实仍由项目文档、engineering-design-fact-base 或明确指定的知识库维护；
- 跨 Agent 的正式长期上下文仍可由 github-shared-memory 等专用 Skill 维护；
- 不自动写入凭据、私密用户信息、未确认推测或大段原始对话。

## 4. 默认模型策略

除非用户明确覆盖：

~~~text
最终主控：当前对话模型
执行 Agent：优先 Luna
执行 Agent 推理强度：优先 max
最大并发：按依赖、文件冲突和当前运行环境自动决定
~~~

只有执行后端明确支持模型/推理强度选择时，才显式请求 Luna + max。

若 Ruflo 或其他后端不能保证该模型：

- 使用当前后端可用的最接近配置；
- 记录实际使用的模型/路由；
- 不得声称使用了并未实际使用的模型；
- 用户明确指定模型时不得静默替换。

## 5. 角色池

### Explorer

只读调查、定位、方案对比、日志分析、依赖关系和风险识别。默认不修改业务文件。

### Worker

负责实际修改。必须：

- 只修改授权范围；
- 遵守冻结接口和主控方案；
- 保留用户已有修改；
- 不擅自扩大范围；
- 完成本地自测；
- 返回修改清单、实际命令、结果、警告和遗留项；
- 不自行宣布最终验收。

### Tester

独立验证，不默认相信 Worker 自测。负责复现、回归、边界、负向测试、静态检查和原始结果核对。

Tester 原则上不直接修业务代码，问题返回主控后再交给 Worker。

### Reviewer

对抗式审查，重点查：

- 是否真正满足需求；
- 是否硬编码结果或绕过逻辑；
- 是否遗漏错误路径和边界条件；
- 是否破坏未授权接口；
- 是否覆盖用户已有修改；
- 测试是否真的测到目标；
- 是否留下临时文件、后台进程或外部副作用。

高风险任务可以派两个互不参考结论的 Reviewer。

## 6. 先构建任务拓扑，再并行

主控先把任务拆成节点，并记录：

- 读/写属性；
- 输入与输出；
- 文件所有权；
- 前置依赖；
- 是否可并行；
- DONE WHEN；
- 必跑验证。

例如：

~~~text
A：调查协议和接口，只读
B：修改模块 X
C：修改模块 Y
D：集成 X/Y，依赖 B/C
E：最终测试，依赖 D

A ───────────────┐
B ──┐             │
    ├─→ D ────────┼─→ E
C ──┘             │
~~~

可以并行：

- 独立只读调查；
- 不同文件且接口稳定的修改；
- 独立测试；
- 独立审核。

必须串行：

- 后一节点依赖前一节点结果；
- 多 Agent 会修改同一文件；
- 接口尚未冻结；
- 前一任务会改变后一任务的输入或测试基线。

Ruflo 只执行这张图，不替主控决定依赖关系。

## 7. 子 Agent 上下文最小化

主控保留全局上下文，子 Agent 只接收当前任务真正需要的信息。

标准任务包：

~~~text
TASK
要完成什么。

INPUT
真正需要的文件、证据、上下文、前置结果。

OWNERSHIP
允许读什么；允许改什么。

CONSTRAINTS
禁止修改项、接口、兼容性、用户特殊要求。

DONE WHEN
可判定完成条件和必须执行的验证。

RETURN
修改清单、关键结论、真实测试结果、失败/警告、剩余风险。
~~~

不要向所有 Agent 复制完整长对话，也不要发送“把项目做好”之类无法验收的任务。

## 8. 验收基线

派发前至少冻结：

- 最终交付物；
- 功能要求；
- 接口和兼容性；
- 禁止修改范围；
- 必跑测试或人工核对项；
- 清理要求；
- 已知风险与允许残余差异。

只有会改变架构、外部状态或目标的关键歧义才询问用户；普通实现细节由主控作保守判断。

## 9. 执行与返修

Worker 返回“完成”只代表该节点结束，不代表任务验收。

失败升级：

~~~text
第一次同类失败
→ 原 Worker 根据明确证据修复

第二次同类失败
→ 独立 Explorer / Reviewer 分析根因

第三次同类失败
→ 主控重新审视方案、接口或拆分方式

仍无法解决
→ 停止无效循环，报告 blocker、证据和剩余选择
~~~

Ruflo 的 autopilot、loop worker、后台定时任务或长时间自治模式默认不自动开启；只有任务明确需要且用户已授权时使用。

## 10. 最终验收

至少检查：

1. 修改文件是否符合授权范围；
2. 关键实现是否满足需求；
3. 接口和依赖是否一致；
4. 用户原有修改是否被保留；
5. 测试是否真实运行；
6. 退出码、失败计数、告警是否真实；
7. 是否存在硬编码、伪覆盖、无界等待或绕过验证；
8. 临时产物和外部副作用是否收口。

对于关键任务，必须有独立 Tester 或 Reviewer；主控还应独立复核至少一项最高风险或最终集成验证。

只有以下条件同时满足才能宣布完成：

- 必需节点均结束；
- 发现的问题已修复或被明确接受；
- 必跑测试达到标准；
- 主控完成独立检查；
- 没有未说明的 blocker、失败、警告或副作用。

## 11. 安全与权限

- 多 Agent 不扩大用户授权；
- 删除、发布、外部写入和破坏性操作仍按原任务权限执行；
- Worker 不得越权修改其他节点文件；
- Reviewer 不得以“顺手修复”为理由绕过所有权；
- 共享工作区必须保护用户和其他 Agent 的已有修改；
- 用户改变范围时只重排受影响节点；
- Ruflo 的 memory、federation、后台 worker 和自动学习功能不得成为泄露代码、凭据或个人信息的通道。

## 12. 触发示例

- “这项工作拆几个子 Agent 并行做，你最后统一审核。”
- “Ruflo 负责执行，你在当前对话做最终主控。”
- “Luna max 做 Worker，Tester 独立验证。”
- “两个 Reviewer 分别审核 RTL，不要互相参考。”
- “先并行调查三个方案，再进入实现。”
- “多模块分别修改，最后统一回归和验收。”
