# RTL Pre-TB Review

## 目标

这个 Review 位于：

```text
module_contract.md
        ↓
rtl_design.md
        ↓
RTL Coding
        ↓
Pre-TB Review
        ↓ PASS
TB / Simulation
```

它只回答一件事：

> 当前 RTL 是否存在进入 TB 前就应该发现和修掉的明显问题？

这不是完整验证，也不要求证明 RTL 已经正确。

---

## 输入

必须读取：

1. 当前正式 RTL；
2. `module_contract.md`；
3. `rtl_design.md`；
4. 与当前模块直接相关的接口、公共定义和项目规则。

如果项目已有 `synthesizable-human-rtl`，同时应用其可综合性和代码审查规则，但本 Skill 只保留进入 TB 前最值得快速检查的项目。

---

# Review 范围

## 1. Interface

检查：

- 端口是否缺失、接错、方向错误；
- 位宽是否与 Contract 和上下游一致；
- 参数、宏、类型是否使用正确；
- 是否擅自增加或改变 Contract 未批准的外部行为。

发现接口或职责与 Contract 不一致时，不能把它当普通代码问题直接合理化。

---

## 2. 驱动与组合逻辑

重点检查：

- 多驱动；
- 组合逻辑漏赋值导致 latch；
- 未声明或悬空的关键信号；
- 同一寄存器在多个时序块中驱动；
- 时序块和组合块赋值语义明显错误；
- 明显的仿真/综合不一致风险。

---

## 3. Reset

检查：

- reset 极性和同步/异步方式是否与设计一致；
- 控制状态、valid、错误状态、关键计数器是否有合理复位；
- reset 后模块是否能回到明确的可工作状态；
- 是否存在复位遗漏导致首次事务不确定。

不要求为了“整齐”给所有大容量数据寄存器强行加复位。

---

## 4. FSM / 控制流程

只查明显问题，不重新设计状态机。

检查：

- 是否有明显死状态；
- 是否存在无法到达或无法退出的关键状态；
- 是否漏掉必须的默认恢复路径；
- 状态跳转是否与 `rtl_design.md` 的主流程冲突；
- 同拍多事件时优先级是否明确；
- AI 是否为了简化状态机偷偷改变了关键设计语义。

FSM 拆成几个状态本身不是问题，只要外部功能和关键时序不变。

---

## 5. valid / ready / 握手

如果模块存在握手，重点检查：

- 是否只有在约定的握手条件成立时才推进事务；
- `valid=1 && ready=0` 时需要保持的输出是否稳定；
- 握手和新结果同拍发生时是否会丢数据；
- 是否把 `ready`、`valid` 错当成单拍脉冲；
- 是否违反 `rtl_design.md` 中已经确定的交付时序。

---

## 6. Counter / Timing

检查最常见的时序错误：

- off-by-one；
- 计数起点或清零条件明显错误；
- 最后一拍判断使用旧值/新值混淆；
- 计数器溢出、下溢；
- timeout 条件与设计语义不一致；
- 关键边界拍上多个事件优先级不明确。

如果“计时到底从哪个事件开始”在 `rtl_design.md` 中没有定义，而这个选择会影响功能或验证结果，则不要猜，退回 Design Gate 询问用户。

---

## 7. Width / Signedness / Boundary

检查：

- 截断或扩展；
- signed / unsigned 混用；
- 拼接、切片范围错误；
- 常量位宽不明确；
- 最大值、0、最后一个元素等明显边界条件；
- 地址和深度计算明显越界。

---

## 8. 与设计文档的一致性

重点不是逐行对照文档，而是检查：

- Contract 的接口、职责、Capabilities 是否仍成立；
- Design 中的主流程是否被实现；
- 关键时序是否被改变；
- 关键设计语义是否被改变；
- 是否出现 Design 未定义但会影响功能、职责、接口、关键时序、错误处理或数据语义的新决定。

如果发现最后一种情况：

> 停止把它当普通 Review 问题继续修，先让用户确认设计决定。

---

# 不做什么

本阶段默认不做：

- 不编写 TB；
- 不用波形证明功能正确；
- 不做完整协议覆盖；
- 不做随机验证；
- 不因为“感觉可能更好”重构整个 RTL；
- 不把代码风格问题升级成 Blocking，除非它已经影响正确性或后续验证。

如果编译器、lint 或综合工具可用，可以运行轻量检查帮助发现语法、驱动、宽度等问题，但工具 PASS 不等于 Review PASS。

---

# 问题分类

只分两级：

## Blocking

进入 TB 前必须处理，例如：

- 编译错误；
- 接口不一致；
- 多驱动 / latch；
- reset 明显错误；
- FSM 明显走不通；
- 关键时序违反已确认设计；
- 明显 off-by-one；
- 会导致功能错误的位宽、边界或握手问题；
- 出现未经确认的关键设计决定。

## Warning

不阻塞进入 TB，但建议后续处理，例如：

- 可读性较差；
- 局部结构可以更清楚；
- 不影响当前功能的冗余逻辑；
- 工具相关但尚未证实的问题。

Warning 不应为了凑数量而生成。

---

# 输出格式

默认只输出很短的 Review 结果：

```markdown
# RTL Review

## Blocking
- 无

## Warning
- W01：...

## Result
PASS
```

如果存在 Blocking：

```markdown
# RTL Review

## Blocking
- B01：`valid_o` 在 `ready_i=0` 时仍被下一状态覆盖，与已确认保持语义冲突。
- B02：`data_cnt_reg + 1` 的结束条件少覆盖最后一个数据字。

## Warning
- 无

## Result
FAIL
```

每条问题只写：

> 位置 / 现象 / 为什么是问题 / 最小修改方向

不要写成长篇代码评审报告。

---

# Gate

只有满足以下条件才能进入 TB 阶段：

1. RTL 可正常编译或至少不存在已知语法阻塞；
2. `Blocking = 0`；
3. 没有待用户确认的关键设计问题。

Warning 可以保留进入 TB，但应记录清楚。

总结：

> Pre-TB Review 负责清掉明显问题；TB 才负责证明设计在验证计划覆盖范围内是否正确。
