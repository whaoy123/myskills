# Thesis Opening Report Reviser

用于**执行开题报告整体修订**。本 Skill 的职责是把“审核意见 + 使用者决策”落实到 `.docx` 修改件中，并在修改后重新调用审核 Skill 验证结果。

本 Skill **不是审核器**。它不负责从头发现问题，也不自行制定学校规则、学术标准或修改方向。问题发现、风险分级和学校模板核对应由 `thesis-opening-report-auditor` 完成；本 Skill 只负责把已经明确的修改方案安全、可追踪地执行到 Word 文档中。

## 与审核 Skill 的固定分工

### `thesis-opening-report-auditor`

负责：

- 读取学校模板、通知和用户约束；
- 检查结构、目录、交叉引用、参考文献、题注、缩写、格式、批注、修订、提交风险；
- 给出 P0/P1/P2/P3 问题清单；
- 对技术表述或内容风险给出“建议修改 / 只批注 / 保留不改”等候选方案；
- 修改完成后再次执行复核。

### `thesis-opening-report-reviser`

负责：

- 读取审核结果；
- 读取用户对每个问题的最终处理要求；
- 将两者合并成确定的执行清单；
- 修改 DOCX 副本；
- 对实际修改位置按用户要求添加批注/修订标记；
- 执行结构和字段级自检；
- **再次调用 `thesis-opening-report-auditor` 对修改件复核**；
- 根据复核结果决定是否需要继续修复。

审核 Skill 和修订 Skill 不得互相替代。

## 适用场景

当用户已经有一份审核报告，并说以下类似要求时使用：

- “按刚才审核结果改一下”；
- “这些问题我已经逐项告诉你怎么处理了，开始修”；
- “技术风险只加批注，格式问题直接修”；
- “目录和交叉引用重新插入，引用按顺序重排”；
- “所有修改位置加标注，改完再审一遍”；
- “在 V3.1 上修正，不改原文件”。

如果用户只说“检查 / 审一下 / 找问题”，不要使用本 Skill，应调用审核 Skill。

## 输入契约

开始执行前必须具备以下输入：

1. **源 DOCX**；
2. **最近一次审核结果**，至少包含问题编号、位置、严重级别、问题描述和建议方案；
3. **用户处理要求**，明确哪些问题：
   - 直接修改；
   - 只加批注；
   - 暂不修改；
   - 删除；
   - 恢复旧版本内容；
   - 需要估算后填入；
   - 需要再次确认；
4. 学校模板/要求文件（若审核 Skill 已登记，可沿用其已确认规则）；
5. 输出版本名或明确的版本链；
6. 是否要求所有修改位置增加 Word 批注。

如果审核意见与用户要求冲突，优先级固定为：

> 当前用户明确要求 > 已确认学校要求 > 审核 Skill 建议 > 通用修复习惯

不得用审核 Skill 的默认建议覆盖用户明确决策。

## 核心原则

### 1. 只执行已授权的修改

修订范围来自：

```text
执行范围 = 审核问题清单 ∩ 用户授权处理项
```

另加用户在当前轮明确新增的修改项。

不得因为在修改过程中“顺便发现了别的问题”就直接改。新发现的问题必须：

- 记录为 `new_issue`；
- 若属于明显机械错误且用户已授权“同类问题统一修复”，可一并处理；
- 其他情况留给后续审核 Skill 报告。

### 2. 原文件保护

默认：

- 保留源文件不变；
- 创建明确命名的修改副本；
- 所有结构重建、字段修复、批注写入只作用于副本。

只有用户明确要求覆盖原文件时才允许覆盖。

### 3. 先形成执行矩阵，再改文件

真正写入前必须生成内部 `revision_plan`：

| issue_id | location | audit_recommendation | user_decision | action | annotation | status |
|---|---|---|---|---|---|---|

其中 `action` 只能来自明确动作，例如：

- `replace_text`
- `insert_text`
- `delete_text`
- `add_comment_only`
- `rebuild_field`
- `rebuild_toc`
- `rebuild_caption`
- `rebuild_citation`
- `reorder_references`
- `repeat_table_header`
- `normalize_spacing`
- `define_abbreviation`
- `restore_from_prior_version`
- `leave_unchanged`

没有明确动作的问题不得进入写入阶段。

### 4. 内容风险与机械修复分开

**机械/结构类问题**通常可直接修：

- 目录；
- 标题样式；
- 图表题注；
- REF / SEQ / TOC 字段；
- 参考文献顺序编码；
- 上角标；
- 重复编号；
- 表格重复表头；
- 中英文边界空格；
- 明确的异常空格；
- 已确认的缩写首次定义；
- 元数据或提交前清理项（用户授权时）。

**内容/技术风险类问题**必须严格按用户处理方式：

- 用户说“只批注” → 不改原句，只加批注；
- 用户说“先估一个值填上” → 允许填入，但必须标注“阶段性指标 / 待实测确认”等语义；
- 用户说“先不改” → 保留原文；
- 用户要求增强论证 → 只在有明确来源、旧版本证据或经用户授权的外部证据时补充，不凭模型记忆虚构事实。

### 5. 所有实际修改必须可追踪

如果用户要求“所有修改位置增加标注”：

- 每个实际修改段落或对象都必须有 Word 批注；
- 同一段内多个同类机械修改可合并为一条批注；
- 批注应说明“改了什么 + 为什么改”，不写冗长推理；
- 原有批注默认保留；
- 只批注不修改的风险项必须锚定到对应原文。

不得用颜色、荧光或普通括号文字代替 Word 批注，除非用户明确要求。

## 标准执行流程

### 第 1 步：读取审核结果与用户决策

提取：

- P0/P1/P2/P3 问题；
- 每个问题的位置；
- 审核建议；
- 用户当前轮对各项的处理意见；
- 暂缓项；
- 保护项；
- 必须保留的原批注；
- 是否需要查历史版本。

输出内部 `revision_plan`，确认不存在未决动作后再修改。

### 第 2 步：必要时读取历史版本

仅在以下情况查旧版本：

- 审核指出疑似误删；
- 用户要求“看前几个版本是不是删掉了”；
- 当前字段/格式已经损坏，但旧版本存在正确结构；
- 需要确认原引用位置或原始论证段落。

旧版本只作为证据和恢复来源，不能整段覆盖当前版本的新内容。

### 第 3 步：创建修改副本

- 复制源 DOCX；
- 记录源文件指纹和目标文件名；
- 确认副本可以用 `python-docx` / OOXML 正常开包；
- 后续所有操作只写副本。

### 第 4 步：执行机械与结构修复

根据 `revision_plan` 执行已授权项。

常见子流程包括：

#### 目录与交叉引用

- 重新建立或修复 `TOC`、`REF`、`SEQ`、书签；
- 图、表、章节引用目标必须存在；
- 不把字段静态化；
- 不能只改字段显示文本而不修 instruction/书签关系。

#### 参考文献系统

当审核意见要求重排/修复引用时，必须执行完整闭环，而不是局部改数字：

1. 扫描正文文献 `REF` 首次出现顺序；
2. 建立 `old_ref -> new_ref` 映射；
3. 按首次引用顺序重排文后条目；
4. 参考文献编号只保留一个来源；
5. 重建 `RefNum...` 书签和正文 `REF`；
6. 统一正文引用 token 的上角标；
7. 检查无 `[8] 8AUTHOR...` 双重编号；
8. 首次引用序列必须严格为 `1,2,3,...,N`。

需要更复杂的专项实现时，可调用独立 citation/rebuilder skill，但最终结果仍由本 Skill 统筹并交给审核 Skill 复核。

#### 图表与表格

- 题注统一使用正确 `SEQ` 字段；
- 图/表编号连续；
- 题注内部空格按模板统一；
- 跨页表格按审核意见设置重复表头；
- 不随意改变用户确认可接受的图形尺寸与布局。

#### 缩写与空格

- 仅对审核 Skill 已指出或用户授权的缩写补首次定义；
- DDR、JTAG 等用户明确豁免的常用缩写不强制展开；
- 中英文/数字边界空格按已确认规则统一；
- 删除异常空格时避免破坏 URL、字段指令、单位和英文短语内部空格。

### 第 5 步：执行内容类修改或批注

- 技术风险只按用户要求处理；
- 需要填估算指标时，应写成可验证、保守、阶段性的指标，并在批注中说明来源/假设；
- 需要增强论证时优先使用：当前报告已有证据 → 历史版本 → 用户提供资料 → 经授权的外部来源；
- 无依据时宁可批注“待补证据”，不得编造。

### 第 6 步：字段与 OOXML 自检

至少检查：

- DOCX 可正常开包；
- `TOC`、`REF`、`SEQ` 字段结构完整；
- 所有 REF 目标书签存在；
- 参考文献无双重编号、漏号、重复号；
- 文献正文首次引用顺序正确；
- 图表引用目标存在；
- 批注锚点有效；
- 原批注数量没有异常减少；
- 未引入新的隐藏文本；
- 未意外引入修订 `w:ins/w:del`；
- 保护项没有改变。

### 第 7 步：字段更新与视觉复核

优先：

1. Microsoft Word 可用时，在副本上更新全部域；
2. 无 Word 自动化时，更新安全可确定的缓存值，并设 dirty/update-on-open；
3. 使用渲染 PDF/页面图做视觉检查；
4. 不把 LibreOffice 另存后的 DOCX 作为 Word 字段语义正确的唯一证据。

如果无法执行 Word 的最终域刷新，必须明确记录：

```text
FIELD_REFRESH_REQUIRED_IN_WORD
```

不能声称“Word 中最终显示已完全验证”。

### 第 8 步：必须再次调用审核 Skill

这是本 Skill 的强制闭环步骤。

修改件完成后，必须把：

- 修改后的 DOCX；
- 原学校要求/模板；
- 用户保护项；
- 本轮修改摘要；

重新交给 `thesis-opening-report-auditor`。

审核 Skill 必须重新执行至少以下检查：

- 原 P0/P1 是否消除；
- 原 P2/P3 是否按用户要求处理；
- 是否因修改引入新问题；
- 目录与标题是否一致；
- 交叉引用/题注/参考文献字段是否完整；
- 文献顺序与上角标是否正确；
- 表格分页、图题、空格、缩写是否合规；
- 批注和保护项是否符合用户要求；
- 最终视觉渲染是否异常。

### 第 9 步：根据复核结果闭环

审核返回：

#### PASS

- 停止修改；
- 输出最终文件和修改摘要。

#### PASS_WITH_WARNINGS

- 如果 warning 对应用户明确“暂不修改 / 只批注”的项目，可接受并停止；
- 其他 warning 进入下一轮 `revision_plan`。

#### FAIL

- 不得交付为“最终版”；
- 将失败项转回修订计划；
- 修复后再次调用审核 Skill；
- 直到 PASS 或用户明确接受剩余风险。

## 强制验收条件

本 Skill 自己的执行结果至少满足：

1. 源文件未被意外覆盖；
2. 所有实际修改都来自审核意见或用户明确新增要求；
3. 暂缓项未被修改；
4. 只批注项原文未被改变；
5. 要求标注的修改位置均有批注；
6. DOCX 可正常开包；
7. 交叉引用、题注、参考文献等结构字段没有被静态化；
8. 没有因批量替换破坏 URL、单位、英文短语或字段指令；
9. 已执行修改后审核；
10. 最终状态来自审核 Skill，而不是修订 Skill 自己宣布通过。

若第 9 或 10 项未满足，本 Skill 只能输出：

```text
REVISION_DONE_BUT_REAUDIT_NOT_COMPLETED
```

不能称为最终定稿。

## 输出格式

最终向用户只报告：

1. 修改件文件名；
2. 本轮执行了哪些审核问题；
3. 哪些问题按用户要求只批注/暂缓；
4. 修改后审核结果：`PASS / PASS_WITH_WARNINGS / FAIL`；
5. 剩余 warning（如有）；
6. Word 域是否仍需要人工 `Ctrl+A -> F9`；
7. 文件链接/路径。

不要在最终回复中重复完整内部推理。
